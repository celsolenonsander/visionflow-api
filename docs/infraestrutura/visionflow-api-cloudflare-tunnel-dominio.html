3. Pré-requisitos e diagnóstico inicial

Em uma máquina Ubuntu nova, atualize os pacotes e instale ferramentas básicas. Este é um procedimento recomendado para preparar o ambiente; não representa necessariamente o histórico exato dos comandos usados na máquina atual.

sudo apt update
sudo apt install -y git curl ca-certificates

Verifique o ambiente:

lsb_release -a
uname -m
git --version
curl --version

O sistema atual é Ubuntu 24.04 LTS e a arquitetura observada é x86_64. A versão do Go deve ser compatível com a diretiva go do arquivo go.mod e com o projeto.

4. Instalação/validação do Go

No ambiente atual, o comando go version retornou go1.24.9 linux/amd64. Para não sobrescrever uma instalação funcional, primeiro verifique:

go version
which go
go env GOPATH
go env GOMOD

Se Go não estiver instalado, consulte o procedimento oficial de instalação para Linux e escolha uma versão compatível com o go.mod: https://go.dev/doc/install. Após a instalação, abra um novo terminal e valide com go version. Evite manter duas instalações diferentes de Go no PATH.

5. Obter o código e instalar dependências

O caminho local conhecido é ~/Documents/VisionFlow_1/visionflow-api. Para uma máquina nova, clone o repositório Git oficial do projeto. O endereço remoto não foi registrado neste documento; consulte o campo remoto no computador atual:

cd ~/Documents/VisionFlow_1/visionflow-api
git remote -v
git status
cat go.mod

Em uma máquina nova, use o endereço confirmado por git remote -v:

mkdir -p ~/Documents/VisionFlow_1
cd ~/Documents/VisionFlow_1
git clone <URL_DO_REPOSITORIO_VISIONFLOW_API> visionflow-api
cd visionflow-api

Substitua <URL_DO_REPOSITORIO_VISIONFLOW_API> pela URL real do repositório. Não adivinhe nem publique credenciais embutidas na URL.

Baixe e valide as dependências Go declaradas pelo projeto:

go mod download
go mod verify
go test ./...

Se os testes passarem, compile a API:

go build -o ./bin/visionflow-api ./cmd/api

Se a compilação reclamar de dependências ou versão, confira go.mod e go.sum. Não remova nem regenere esses arquivos sem entender a alteração.

6. Executar e testar a API localmente

O comando usado durante a configuração foi:

cd ~/Documents/VisionFlow_1/visionflow-api
go run ./cmd/api

Mantenha esse terminal aberto enquanto estiver usando a execução manual. Em outro terminal, teste:

curl -i http://localhost:8080/health

Resultado esperado: HTTP 200 e resposta semelhante a:

{"success":true,"data":{"status":"ok"},"error":null}

Swagger local, quando a API estiver em execução:

http://localhost:8080/swagger/index.html

Se a porta estiver ocupada, identifique o processo antes de encerrá-lo:

sudo ss -ltnp | grep ':8080'

11. Configurar a API como serviço systemd — pendente

Esta etapa ainda não foi executada. A API estava rodando com go run ./cmd/api. Antes de criar o serviço, é necessário confirmar:

  • o caminho final do binário compilado;
  • o usuário Linux que deve executar a API;
  • as variáveis de ambiente obrigatórias;
  • o diretório de trabalho correto;
  • se a API precisa de acesso ao PostgreSQL e como as credenciais serão fornecidas com segurança.

Não crie um arquivo systemd definitivo com valores presumidos. Depois de confirmar esses detalhes, documente a unidade do serviço, permissões, comando de ativação e os comandos de diagnóstico. Os comandos de operação normalmente usados serão:

sudo systemctl status visionflow-api --no-pager
sudo journalctl -u visionflow-api -n 100 --no-pager
sudo journalctl -u visionflow-api -f

Esses comandos só funcionarão depois que a unidade visionflow-api for criada e habilitada.

12. Variáveis de ambiente e segredos

  • Não versionar senhas, tokens JWT, tokens Cloudflare, chaves privadas ou credenciais do banco.
  • Usar variáveis de ambiente ou um arquivo de configuração protegido por permissões do sistema.
  • Se for usado um arquivo de ambiente para systemd, restringir leitura ao usuário/root apropriado e não adicioná-lo ao Git.
  • Manter um arquivo de exemplo, como .env.example, apenas com nomes de variáveis e valores fictícios, se o projeto usar esse padrão.
  • Confirmar que logs não registram tokens, senhas ou dados sensíveis.

13. PostgreSQL e segurança

  • Não publicar a porta TCP 5432 para a internet.
  • Se a API usa PostgreSQL, manter o banco acessível apenas pela rede local/privada necessária.
  • Validar autenticação e autorização no backend; não confiar em um tenant_id enviado pelo frontend para isolar empresas.
  • Configurar CORS permitindo somente as origens reais do frontend.
  • Verificar que endpoints de Swagger e diagnóstico estejam adequados ao ambiente de produção.
  • Usar HTTPS no acesso público e manter Ubuntu, Go e cloudflared atualizados.

14. Problema encontrado durante a configuração

A primeira rota usava api.forcadevendas.programadordelphi.com.br e falhava na negociação TLS. O painel avisava que subdomínios com vários níveis podem exigir Advanced Certificate Manager. A rota foi alterada para api.programadordelphi.com.br, preservando a origem http://localhost:8080. Depois da alteração, o teste público retornou HTTP 200.
