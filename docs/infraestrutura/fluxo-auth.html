🔐 VisionFlow API

Fluxo de Autenticação, Multi-Tenant e Row-Level Security

📋 Visão Geral

A VisionFlow API é um SaaS multi-tenant com 3 níveis de isolamento: Revendedor (white label) → Tenant (cliente) → Empresa (CNPJ). O isolamento de dados é feito via Row-Level Security (RLS) do PostgreSQL, garantindo que mesmo bugs na API não vazem dados entre tenants.

┌─────────────────────────────────────────────────────────────┐ │ REVENDEDOR (white label — opcional) │ │ ├── TENANT (cliente que opera o sistema) │ │ │ ├── EMPRESA 1 (CNPJ matriz) │ │ │ │ └── Cliente / Pedido / Notificação / ... │ │ │ ├── EMPRESA 2 (CNPJ filial) │ │ │ │ └── Cliente / Pedido / Notificação / ... │ │ │ └── USUÁRIO (acessa uma ou mais empresas) │ └─────────────────────────────────────────────────────────────┘

🎯 O que o front precisa saber

Conceito O front manda? O backend resolve?
email + senha ✅ No login —
token (JWT) ✅ Em cada request —
cod_tenant ❌ Nunca ✅ Lê do banco
cod_empresa ❌ Nunca ✅ Lê do banco
cod_usuario ❌ Nunca ✅ Extrai do JWT
⚠️ Regra de ouro: O front nunca envia tenant nem empresa. Tudo é resolvido pelo backend a partir do JWT + tabela usuario_empresa.

🔑 Fluxo 1 — Login

1
Front envia credenciais
POST /auth/login
Content-Type: application/json

{
  "email": "admin@epare.com.br",
  "senha": "123456"
}
2
Backend consulta o banco
SELECT u.cod_usuario, u.nome, u.email
FROM usuario u
JOIN usuario_empresa ue ON ue.cod_usuario = u.cod_usuario
JOIN empresa e ON e.cod_tenant = ue.cod_tenant
               AND e.cod_empresa = ue.cod_empresa
JOIN tenant t ON t.cod_tenant = u.cod_tenant
WHERE lower(u.email) = lower($1)
  AND u.ativo = true
  AND e.ativo = true
  AND t.ativo = true
  AND crypt($2, u.senha_hash) = u.senha_hash
ORDER BY ue.empresa_padrao DESC, ue.cod_empresa ASC
LIMIT 1
3
Backend emite JWT
{
  "sub": 1,           // cod_usuario
  "iat": 1792077419,  // emitido em
  "exp": 1792106219   // expira em 8h
}
⚠️ Importante: O JWT não contém cod_tenant nem cod_empresa. Só o sub (cod_usuario).
4
Backend responde
✅ 200 OK
{
  "success": true,
  "data": {
    "usuario": {
      "id": 1,
      "nome": "Administrador",
      "email": "admin@epare.com.br",
      "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
    }
  },
  "error": null
}
5
Front guarda o token

Salva em localStorage (chave visionflow:auth):

localStorage.setItem('visionflow:auth', JSON.stringify({
  state: {
    user: { id, nome, email },
    token: "eyJ..."
  }
}))

🔄 Fluxo 2 — Requisição autenticada

1
Front envia request com token
GET /clientes
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
2
Middleware Auth valida o JWT
// 1. Extrai o token do header
tokenStr := extractBearerToken(r)

// 2. Valida a assinatura
claims := parseToken(tokenStr)
// claims = { sub: 1, iat: ..., exp: ... }

// 3. Extrai o cod_usuario
userID := extractUserID(claims)  // = 1
3
Middleware resolve tenant/empresa
SELECT cod_tenant, cod_empresa
FROM usuario_empresa
WHERE cod_usuario = $1
ORDER BY empresa_padrao DESC, cod_empresa ASC
LIMIT 1

-- Resultado: cod_tenant = 1, cod_empresa = 1
⚠️ Essa query roda FORA do RLS — a sessão ainda não tem SET LOCAL app.cod_tenant. Por isso ela usa o pool direto, não a Session.
4
Middleware injeta no contexto
ctx := context.WithValue(r.Context(), "user_id", 1)
ctx = context.WithValue(ctx, "tenant_id", 1)
ctx = context.WithValue(ctx, "empresa_id", 1)

next.ServeHTTP(w, r.WithContext(ctx))
5
Handler abre Session com RLS

O service faz:

sess, _ := db.NewSession(ctx, pool, tenantID=1, empresaID=1)

// Dentro de NewSession:
BEGIN;
SELECT set_config('app.cod_tenant', '1', true);
SELECT set_config('app.cod_empresa', '1', true);
💡 Por que set_config e não SET LOCAL? SET LOCAL não aceita placeholders ($1). set_config('app.cod_tenant', $1, true) aceita e o true faz o escopo ser da transação.
6
Query é executada
-- Repository escreve SEM mencionar tenant/empresa:
SELECT codigo, codigo_erp, nome_razao_social, ...
FROM cliente
WHERE codigo > $1
ORDER BY codigo ASC
LIMIT $2
7
PostgreSQL aplica RLS automaticamente
-- A query acima vira efetivamente:
SELECT codigo, codigo_erp, nome_razao_social, ...
FROM cliente
WHERE codigo > $1
  AND cod_tenant = fn_current_tenant()       -- = 1
  AND (fn_current_empresa() IS NULL
       OR cod_empresa = fn_current_empresa()) -- = 1
ORDER BY codigo ASC
LIMIT $2

As funções fn_current_tenant() e fn_current_empresa() leem as variáveis app.cod_tenant e app.cod_empresa que foram setadas via set_config.

8
Backend responde
✅ 200 OK
{
  "success": true,
  "data": {
    "items": [
      {
        "id": 1,
        "codigo_erp": "000001",
        "nome_razao_social": "CLIENTE TESTE LTDA",
        "cnpj_cpf": "22.222.222/0001-22",
        ...
      }
    ],
    "nextCursor": null
  },
  "error": null
}

🛡️ Por que RLS importa

Cenário Sem RLS Com RLS
Dev esquece WHERE cod_tenant Vaza dados Bloqueado
SQL injection altera query Vaza dados Bloqueado
Token roubado de outro tenant Vaza dados Bloqueado
Bug em filtro de relatório Vaza dados Bloqueado

🧪 Validação end-to-end

Provado em 2026-10-15 com os seguintes testes:

Teste Resultado
Sem contexto RLS SELECT COUNT(*) FROM cliente → 0
Tenant 1 SELECT COUNT(*) FROM cliente → 1
Tenant 4 SELECT COUNT(*) FROM cliente → 30
Tenant 1 tentando ver tenant 4 Bloqueado
API: user 1 → GET /clientes Retorna 1 cliente
API: user 3 → GET /clientes Retorna 30 clientes

⚠️ O que o front NÃO precisa fazer

  • ❌ Enviar cod_tenant em query/body
  • ❌ Enviar cod_empresa em query/body
  • ❌ Gerenciar troca de empresa (ainda não implementado)
  • ❌ Filtrar por tenant manualmente
  • ❌ Decodificar JWT (o backend já resolve tudo)

✅ O que o front PRECISA fazer

  • ✅ Fazer login com email + senha
  • ✅ Guardar o token após login
  • ✅ Enviar Authorization: Bearer <token> em toda requisição autenticada
  • ✅ Tratar 401 (token inválido/expirado) → redirecionar pra login
  • ✅ Tratar 403 (sem permissão) quando aparecer

📚 Glossário

Termo Significado
Tenant Cliente do revendedor que opera o sistema. Nível de billing e limites.
Empresa CNPJ do tenant. Um tenant pode ter várias (matriz + filiais).
RLS Row-Level Security — filtro automático por linha no PostgreSQL.
JWT JSON Web Token — credencial assinada que identifica o usuário.
Session Transação de banco com contexto de tenant/empresa injetado.
set_config Função PostgreSQL para setar variáveis de sessão dentro de transação.
cursor pagination Paginação por nextCursor em vez de offset/page.
