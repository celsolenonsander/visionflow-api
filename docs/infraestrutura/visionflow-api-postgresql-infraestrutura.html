1. Visão Geral

Este documento descreve passo a passo como instalar, configurar e validar a infraestrutura de banco de dados do VisionFlow API — um sistema SaaS multi-tenant com suporte a white label (revendedores).

O que o sistema faz

  • Força de vendas externa (representantes) usando app mobile/web
  • Multi-tenant — vários clientes na mesma base
  • Multi-empresa — cada cliente pode ter várias filiais (CNPJs)
  • White label — revendedores podem usar a marca própria
  • Isolamento automático via Row-Level Security (RLS)

2. Arquitetura e Decisões

Modelo de dados multi-tenant

O sistema usa 3 níveis de isolamento:

REVENDEDOR (quem revende com marca própria — white label)
    └── TENANT (cliente do revendedor — quem opera o sistema)
            └── EMPRESA (CNPJ do tenant — pode ter várias)
                    └── CLIENTE / ITEM / PEDIDO / ... (dados operacionais)

Por que 3 níveis e não 2?

CamadaPor quê
revendedor Permite white label: cada revendedor usa marca própria (logo, cores, domínio) sem saber que existem outros revendedores. Você (VisionFlow) fica invisível para o cliente final.
tenant Cada cliente do revendedor tem seus próprios dados. É o nível de billing, controle de usuários e limites de uso.
empresa Um tenant pode ter várias filiais (CNPJs diferentes). Ex: "Distribuidora João" tem matriz e 3 filiais.

Por que PostgreSQL e não Firebird?

O ERP dos clientes usa Firebird 2.5, mas o SaaS não pode usar Firebird como banco principal por vários motivos:

  • Firebird 2.5 é de 2010 e está sem atualizações há anos
  • Não tem Row-Level Security (RLS) — isolamento dependia 100% do código da aplicação
  • Migração para nuvem seria muito difícil
  • PostgreSQL é gratuito, suporta RLS nativo, tem ferramentas e comunidade enormes
✅ Decisão Firebird fica apenas no lado do cliente (ERP). Nosso SaaS usa PostgreSQL 16. A integração entre os dois é feita pela camada de API.

Por que RLS?

Row-Level Security faz o banco filtrar dados automaticamente baseado em uma variável de sessão. Vantagens:

  • Se a API esquecer de filtrar por tenant, o banco filtra
  • Impossível vazar dados entre tenants por bug de código
  • Auditoria e LGPD ficam mais simples

Por que codigo_erp e não seu_codigo_*?

Nos layouts originais do integrador, os campos eram chamados seu_codigo_cliente, seu_codigo_item, etc. Era uma convenção do integrador ("o código do cliente no seu ERP"). Na nossa base, renomeamos para codigo_erp porque:

  • Auto-documenta que é um código externo (do ERP)
  • Fica mais curto e direto
  • O ID interno (numérico) já se chama codigo

Por que BOOLEAN no ativo?

O ERP do cliente usa 'A', 'I', 'ADM' para ativo/inativo. Como 'ADM' significa "deixa o sistema decidir", na nossa base:

ERPNossa baseSignificado
'A'TRUEAtivo
'I'FALSEInativo
'ADM'NULLUsa padrão do sistema (geralmente TRUE)

Regra de ouro: se tem ADM ou mais de 2 valores, mantém VARCHAR. Se só tem S/N, vira BOOLEAN.

5. Criação do Banco e Usuário

1

Criar usuário do banco

sudo -u postgres psql

Dentro do psql, execute:

CREATE USER <USUARIO_DB> WITH PASSWORD '<SENHA_FORTE>';
\q

No nosso caso, foi epare. Você pode usar qualquer nome.

2

Criar o banco

sudo -u postgres psql -c "CREATE DATABASE <BANCO> OWNER <USUARIO_DB> ENCODING 'UTF8' TEMPLATE template0;"

No nosso caso: epare_forca_de_vendas.

3

Permitir que o usuário crie bancos (opcional)

sudo -u postgres psql -c "ALTER USER <USUARIO_DB> WITH CREATEDB;"

Isso permite rodar DROP DATABASE e CREATE DATABASE sem depender do postgres.

4

Testar a conexão

psql -h localhost -U <USUARIO_DB> -d <BANCO> -c "SELECT current_user, current_database();"

Saída esperada:

 current_user | current_database
--------------+------------------
 epare        | epare_forca_de_vendas
⚠️ Nunca commitar senhas Guarde a senha em um gerenciador (Bitwarden, 1Password) ou em variável de ambiente. O arquivo .pgpass permite automatizar sem expor no código (veja seção de Backup).

6. Permissões do Schema

⚠️ Importante — PostgreSQL 15+ A partir do PostgreSQL 15, o schema public não permite mais que usuários comuns criem tabelas por padrão. Precisamos ajustar isso manualmente.
1

Definir o usuário como dono do schema public

sudo -u postgres psql -d <BANCO> -c "ALTER SCHEMA public OWNER TO <USUARIO_DB>;"
2

Dar permissões completas

sudo -u postgres psql -d <BANCO> -c "GRANT ALL ON SCHEMA public TO <USUARIO_DB>;"
3

Conferir

sudo -u postgres psql -d <BANCO> -c "\dn+"

Saída esperada:

  Name  | Owner | Access privileges
--------+-------+-------------------
 public | epare | epare=UC/epare
                | =U/epare

O epare precisa ser o Owner.

✅ Por que isso é necessário? Como o schema public pertence ao postgres por padrão, o usuário da API não poderia criar tabelas. Ao transferir a posse, o epare fica autônomo para trabalhar.

11. Parte 5 — Row-Level Security (RLS)

Esta é a parte mais importante para segurança multi-tenant. Vamos ativar RLS em 56 tabelas.

Como funciona

  1. A API autentica o usuário e descobre o cod_tenant
  2. A API executa SET LOCAL app.cod_tenant = '1'; no início da transação
  3. A partir daí, toda query nas tabelas com RLS filtra automaticamente
  4. Mesmo se a API esquecer o WHERE, o banco filtra por ela

Arquivo SQL

~/Documents/<PROJETO>/sql/parte5_rls.sql

Aplicar

psql -h localhost -U <USUARIO_DB> -d <BANCO> -f "~/Documents/<PROJETO>/sql/parte5_rls.sql"

Como a API usa (exemplo)

BEGIN;
SET LOCAL app.cod_tenant = '2';
SET LOCAL app.cod_empresa = '1';   -- opcional
SELECT * FROM cliente;              -- só clientes do tenant 2
COMMIT;
✅ Vantagens do RLS
  • Isolamento provado em nível de banco
  • Bugs de código na API não vazam dados entre tenants
  • Auditoria e LGPD mais simples
⚠️ Detalhes importantes
  • Superuser (postgres) ignora RLS — apenas o usuário da API (epare) respeita
  • Usamos FORCE ROW LEVEL SECURITY para que até o dono da tabela respeite o RLS
  • Sempre use SET LOCAL (não SET) dentro de transação — assim o contexto não vaza entre conexões do pool

12. Testes de Validação

Depois de aplicar tudo, valide com os testes abaixo. Entre no psql:

psql -h localhost -U <USUARIO_DB> -d <BANCO>

Teste 1 — Sem contexto (deve retornar vazio)

SELECT cod_tenant, codigo_erp, nome_razao_social FROM cliente;

Esperado: 0 linhas. Sem contexto definido, RLS bloqueia tudo.

Teste 2 — Contexto do Tenant A

BEGIN;
SET LOCAL app.cod_tenant = '2';
SELECT cod_tenant, codigo_erp, nome_razao_social FROM cliente ORDER BY codigo_erp;
COMMIT;

Esperado: apenas clientes do tenant 2 (ex: A001, A002).

Teste 3 — Contexto do Tenant B

BEGIN;
SET LOCAL app.cod_tenant = '3';
SELECT cod_tenant, codigo_erp, nome_razao_social FROM cliente ORDER BY codigo_erp;
COMMIT;

Esperado: apenas clientes do tenant 3 (ex: B001, B002).

Teste 4 — Tentar burlar (deve dar erro)

BEGIN;
SET LOCAL app.cod_tenant = '2';
INSERT INTO cliente (cod_tenant, cod_empresa, codigo_erp, nome_razao_social, tipo_pessoa, ativo)
VALUES (3, 1, 'HACK001', 'Tentativa de invasão', 'J', TRUE);
COMMIT;

Esperado: ERROR

ERROR: new row violates row-level security policy for table "cliente"

Isso prova que mesmo um bug na API não consegue inserir dados de outro tenant.

Teste 5 — Inserir no tenant correto (deve funcionar)

BEGIN;
SET LOCAL app.cod_tenant = '2';
INSERT INTO cliente (cod_tenant, cod_empresa, codigo_erp, nome_razao_social, tipo_pessoa, ativo)
VALUES (2, 1, 'A003', 'Cliente A3 (novo)', 'J', TRUE);
COMMIT;

Esperado: INSERT 0 1 (sucesso).

✅ Todos os testes devem passar Se algum falhar, verifique se o RLS foi aplicado corretamente e se o usuário do banco não é superuser.

13. Backup Automático

Criar script de backup

mkdir -p ~/Documents/<PROJETO>/scripts
nano ~/Documents/<PROJETO>/scripts/backup.sh

Conteúdo:

#!/bin/bash
# ============================================================
# Backup diário do banco VisionFlow
# ============================================================

set -e

# Configurações
BANCO="<BANCO>"
USUARIO="<USUARIO_DB>"
DESTINO="$HOME/Documents/<PROJETO>/backups"
RETENCAO_DIAS=30
DATA=$(date +%Y-%m-%d_%H-%M)

# Cria diretório se não existir
mkdir -p "$DESTINO"

# Faz o dump e compacta
echo "[$(date)] Iniciando backup de $BANCO..."
pg_dump -h localhost -U "$USUARIO" "$BANCO" | gzip > "$DESTINO/${BANCO}_${DATA}.sql.gz"

# Remove backups antigos
find "$DESTINO" -name "*.sql.gz" -mtime +$RETENCAO_DIAS -delete

echo "[$(date)] Backup concluído: ${BANCO}_${DATA}.sql.gz"

Dar permissão e testar

chmod +x ~/Documents/<PROJETO>/scripts/backup.sh
~/Documents/<PROJETO>/scripts/backup.sh

Automatizar com pgpass (sem senha explícita)

nano ~/.pgpass

Conteúdo (troque pelos valores reais):

localhost:5432:<BANCO>:<USUARIO_DB>:<SENHA_FORTE>

Permissão obrigatória:

chmod 600 ~/.pgpass

Agendar no cron

crontab -e

Adicione (roda todo dia às 3h da manhã):

0 3 * * * /home/<USUARIO_LINUX>/Documents/<PROJETO>/scripts/backup.sh >> /home/<USUARIO_LINUX>/Documents/<PROJETO>/logs/backup.log 2>&1
⚠️ Backups locais não bastam Um backup no mesmo disco do banco não protege contra falha de hardware. Copie periodicamente para:
  • HD externo
  • Nuvem (Google Drive, Dropbox, S3)
  • Outro servidor

14. Troubleshooting

Erro: peer authentication failed for user "postgres"

Causa: tentativa de conectar via TCP como usuário do sistema.

Solução: use sudo -u postgres psql (não psql -U postgres) para conectar localmente.

Erro: password authentication failed for user "postgres"

Causa: o usuário postgres não tem senha definida (é o padrão no Ubuntu).

Solução: definir uma senha:

sudo -u postgres psql -c "ALTER USER postgres WITH PASSWORD '<SENHA_FORTE>';"

Erro: must be owner of schema public

Causa: o schema public pertence ao postgres, não ao usuário da API.

Solução:

sudo -u postgres psql -d <BANCO> -c "ALTER SCHEMA public OWNER TO <USUARIO_DB>;"
sudo -u postgres psql -d <BANCO> -c "GRANT ALL ON SCHEMA public TO <USUARIO_DB>;"

Erro: DROP DATABASE cannot run inside a transaction block

Causa: DROP DATABASE e CREATE DATABASE não rodam dentro de transação.

Solução: ativar Auto-commit no pgAdmin, ou rodar cada comando separadamente via terminal:

sudo -u postgres psql -c "DROP DATABASE IF EXISTS <BANCO>;"
sudo -u postgres psql -c "CREATE DATABASE <BANCO> OWNER <USUARIO_DB>;"

Erro: relation "X" does not exist

Causa: o SQL da parte ainda não foi aplicado, ou você está conectado em banco errado.

Solução: confirme com \dt e reaplique a parte faltante.

RLS não está filtrando

Causa: você está conectado como superuser (postgres) — superuser ignora RLS.

Solução: conecte como o usuário da API (epare).

Pager do psql está atrapalhando

Solução: dentro do psql, \pset pager off. Ou crie ~/.psqlrc com essa linha.

15. Como Recriar do Zero

Se um dia precisar reconstruir o ambiente, siga esta sequência exata:

1. Remover banco antigo (opcional)

sudo -u postgres psql -c "DROP DATABASE IF EXISTS <BANCO>;"

2. Criar banco novo

sudo -u postgres psql -c "CREATE DATABASE <BANCO> OWNER <USUARIO_DB> ENCODING 'UTF8' TEMPLATE template0;"

3. Ajustar schema

sudo -u postgres psql -d <BANCO> -c "ALTER SCHEMA public OWNER TO <USUARIO_DB>;"
sudo -u postgres psql -d <BANCO> -c "GRANT ALL ON SCHEMA public TO <USUARIO_DB>;"

4. Aplicar as 5 partes em ordem

cd ~/Documents/<PROJETO>/sql

psql -h localhost -U <USUARIO_DB> -d <BANCO> -f nucleo_saas.sql
psql -h localhost -U <USUARIO_DB> -d <BANCO> -f cadastros_base.sql
psql -h localhost -U <USUARIO_DB> -d <BANCO> -f cadastros_operacionais.sql
psql -h localhost -U <USUARIO_DB> -d <BANCO> -f tabelas_filho.sql
psql -h localhost -U <USUARIO_DB> -d <BANCO> -f parte5_rls.sql

5. Validar

psql -h localhost -U <USUARIO_DB> -d <BANCO> -c "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='public' AND table_type='BASE TABLE';"

Esperado: 62.

6. Rodar os testes de RLS

Veja seção Testes de Validação.

✅ Sucesso Se todas as 5 partes aplicaram sem erro e os testes de RLS passaram, o ambiente está pronto para receber a API.

16. Glossário

TermoSignificado
Tenant Termo em inglês para "inquilino". No SaaS, é quem te paga a assinatura. Ex: "Distribuidora João".
Revendedor Software house que revende o sistema com marca própria (white label). Ex: "Sistema do Zé" (que é cliente seu).
White Label Produto feito por uma empresa mas vendido com marca de outra. Ex: seu sistema rebrandado pelo revendedor.
Multi-tenant Arquitetura onde vários clientes (tenants) compartilham a mesma base de dados, mas com isolamento lógico.
Row-Level Security (RLS) Recurso do PostgreSQL que filtra linhas automaticamente baseado em política definida.
codigo_erp Código de um registro no ERP do cliente. Serve para casar os dados entre a nossa base e o ERP dele.
slug Identificador amigável para URL (ex: distribuidora-joao em vez de tenant-42).
Firebird Banco de dados usado pelo ERP do cliente. É onde os dados originais vivem.
pg_dump Ferramenta do PostgreSQL para gerar backup lógico (arquivo .sql com todos os dados).
SET LOCAL Comando SQL para definir uma variável de sessão que dura apenas até o final da transação.
Trigger Função executada automaticamente pelo banco quando um evento (INSERT/UPDATE/DELETE) acontece.
Policy (RLS) Regra que define quais linhas são visíveis/editáveis para cada usuário em uma tabela com RLS.
